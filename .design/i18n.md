# Frontend i18n: one file per feature area

## Layout

```
frontend/src/i18n/
  index.ts                 # i18next init, SUPPORTED_LANGUAGES
  locales/
    en/                    # fallback bundle
      index.ts             # spreads every area file into one object
      app.ts               # common, layout, system, help, login, onboarding, ...
      provider.ts          # provider*, credentialPage, apiKeyModal, sharingKeys, teams, accessControl
      rule.ts              # rule, ruleHeader, template*, decisionsGuide, context1M
      dashboard.ts         # dashboard, history
      bench.ts             # bench, probe, playground
      agent.ts             # agent*, scenario*, clientConfigStatus, claudeCode, *Config, prompt, mcp
      remote.ts            # remoteControl, remoteAgent, bots, botAccess, notify, nodes
      image.ts             # image*
    zh/  ru/               # same files, same namespaces per file as en/
```

An area file holds several top-level namespaces (the first segment of a t()
key), grouped by the product area a reader is working on. A namespace lives
in exactly one area; `localeFiles.test.ts` fails if two areas define the same
one (index.ts spreads them, so the later file would silently win) or if a
locale's layout drifts from en/.

The grain is deliberately coarse: one file per namespace gave 55 files per
language, most under 30 lines, which scattered one page's copy across many
tabs. Split an area further only when it grows a clearly separate feature.

## Why plain modules, not i18next namespaces

i18next can load several namespaces (`useTranslation('rule')`,
`t('rule:routing.title')`), but switching to them would change every one of
the ~hundreds of `t()` call sites and the `tKeyCoverage` scan. The size
problem is only in the source files, so the split stays there:
`locales/<lang>/index.ts` reassembles the same single `translation` resource
object i18next has always received. Runtime behaviour, key paths and
`index.ts`'s `resources` are unchanged; the split was verified by bundling
each locale before and after and comparing the key-sorted JSON.

All locales are still bundled eagerly. Lazy per-language loading
(`i18next-resources-to-backend`) is a separate decision if bundle size ever
matters.

## Adding strings

- A key under an existing namespace: edit that namespace in the matching
  area file of every language (`localeParity.test.ts` and
  `tKeyCoverage.test.ts` enforce it).
- A new top-level namespace: add it to the area it belongs to, in every
  language, at the same place.
- A new area file: add it to each language directory and a matching import +
  spread in each `locales/<lang>/index.ts`.
