# Playground 运行卡片的重入(Re-entry)

> 适用对象:tingly-box 前端贡献者。
> 描述 Image Playground 里"产出之后还能回到输入"的三件事:请求重入、
> 素材常驻、prompt 一键复制。
> 关联文档:`ux-principles.md`(§10 完成 ≠ 锁死、§11 交出下一步的物件)、
> `sketch-canvas.md`、`image-slice.md`、`imageedit.md`。

---

## 1. 背景:卡片是终点,不是出口

Playground 的结果区是一条运行卡片的时间线。改动之前,卡片只能做三件事:看大
图、把输出当参考图、失败重试。于是出现三个都指向同一个毛病的摩擦:

1. **不能重入**。想在上一次的基础上改一版——同一组参考图、同样的 size/quality/
   N,只改 prompt 里的两个词——只能手工把参考图重新拖一遍、把 prompt 重新敲一
   遍。卡片记着整个请求,却不肯还回来。
2. **重试看不见素材**。原始参考图的缩略图只画在**已完成**的卡片上。恰恰是失败
   卡片和进行中卡片——"我到底发了什么?"最该被回答的两个状态——什么都不显示,
   Retry 变成盲试。
3. **prompt 只能手选**。卡片上的 prompt 被 clamp 成两行,想拿走全文只能开大图
   预览再复制,或者干脆去输入框里手动全选。

三件事共用一个判断:**"完成"是状态,不是终结**(原则 10),而下一步动作要的物
件应该直接交到手上(原则 11)。

---

## 2. 决策

### 2.1 重入 = 把整个请求放回面板,而不是新开一个编辑器

`handleReuseRun` 把一次运行的 prompt / model / size / quality / count / 参考图
一起写回左侧输入面板(参考图从 `sourceImages` 的 data URL 读回成 `File`,与
`handleRetry` 同源),然后把面板滚回视野。

- **不做"重入对话框"**:面板本身就是这个请求的编辑器,再开一个就是第二处
  prompt(原则 2:能直接进入工作面就不要先选模式)。
- **不做局部重入**(只填 prompt / 只填参考图):那是把一个旋钮拆成四个开关。
  想只要一部分,重入之后在面板里删掉即可——面板的每一项本来就可编辑。
- **model 没有规则时不静默替换**:`model` 是从规则列表推导的,重入一个已经没有
  规则的模型会被 Select 悄悄回落到第一个模型。这里改成显式提示"请先选一个模型",
  绝不用另一个模型替用户做主。
- Retry 与 Reuse 并存,分工清楚:**Retry = 原样再发一次**,**Reuse = 载回来改**。

入口有两个,都在用户产生"再来一版"念头的地方:卡片头部的动作簇,以及大图预览
的工具栏(`SelectedImage.runId` 把图片和它背后的运行关联起来)。

### 2.2 素材在每一个卡片状态都在

原来只在已完成卡片里内联的缩略图行抽成 `RunSourceStrip`,pending / failed /
completed 三种状态共用,点开进同一个 lightbox(`kind: 'source'`)。失败卡片因此
能在重试前先看清自己发了什么;mock 的 `/images/edits` 也补上了 `[fail]` 分支,
这条路径在 mock 模式下可复现。

### 2.3 prompt 一律有复制按钮

`CopyIconButton` 出现在三处:输入框的 endAdornment(有内容时)、放大编辑对话框
的标题栏、每张运行卡片的动作簇。理由很直白:**prompt 是文本,文本不该靠手选**。

卡片的动作簇统一为 `renderRunActions(run, onRemove?)`:复制 prompt / 重入请求 /
移除卡片,三种状态同一个顺序、同一套图标;进行中卡片没有"移除"(Cancel 才是),
所以 `onRemove` 省略。

### 2.4 素材可以从输出直接回到输入

运行卡片上的素材缩略图不只是"看"的:每一张 hover 出一个 `Use as reference` 小
按钮,一键把它加回参考图列表(复用输出图早就有的 `handleUseAsReference`)。缩略
图从 28px 提到 36px,就是为了容得下这个按钮——**素材本身就是下一次请求最可能的
输入**,让它在卡片和输入区之间来回,不该是"下载再上传"。

### 2.5 参考图顺序可拖拽调整

参考图列表**是有序的**——它按顺序进 `images/edits` 请求,顺序对上游有意义。既然
有序,就必须能就地改序,而不是"删掉再按想要的顺序重新加一遍"。

- HTML5 drag:缩略图 `draggable`,拖动中的那张半透明,悬停的落点画一圈主色描边。
- 与"从外部拖文件进来添加"共存靠一个自定义 dataTransfer 类型
  (`application/x-tingly-reference-index`)加上 `draggingReference` 状态:内部拖
  拽在缩略图上就地 `stopPropagation` 处理掉,外部文件继续落到虚线框的添加逻辑。
- 键盘等价物:聚焦某张缩略图后 ←/→ 直接移动它,焦点跟着图片走而不是留在原位。
  拖拽不该是唯一的排序方式。
- 提示文案只在有两张以上时出现——只有一张的时候没有"顺序"可言。

## 3. 检查表对照

| 原则 | 落点 |
|------|------|
| §10 完成 ≠ 锁死 | 产出的卡片可以整份载回输入面板继续编辑 |
| §11 交出下一步的物件 | prompt 一键复制;素材缩略图常驻;重入直接给回可编辑的请求 |
| §12 副作用限定在当前表面 | 重入只写这张卡片所在 Playground 的输入面板,并把面板滚回视野 |
| §4 正交轴 | Retry(原样重发)与 Reuse(载回来改)分开,不做成一个按钮的两种语义 |
| §5 展示具体值 | 参考图顺序就是请求里的顺序,拖拽改的是那个真实顺序,不是一个"排序偏好" |
