# Image Workbench(聚焦工作台)与图片归档

> 适用对象:tingly-box 前后端贡献者。
> 描述生图 Playground 的"聚焦一张图"工作台,以及它所依赖的后端图片归档。
> 关联文档:`image-layout.md`(Playground 布局)、`imageedit.md`(网关链路)、
> `ux-principles.md`(判断标准)。

---

## 1. 背景

生图常常不是"反复生成、反复消失",而是盯住一个角色 / 物品 / 主题,围绕它一张张地出图。
行业里各家都收敛到了同一个形态:Krea Elements、Kling Element Library、getimg Elements、
Higgsfield Soul ID 都把"一组参考图 + 一段文字描述"存成一个可复用的实体。区别主要在
于重量:按次挂参考图 → 存成命名实体 → 训练身份(LoRA)。

我们取最小的一档:**一张根图 + 它的描述 + 从它衍生出来的图**。不训练,与 vendor 无关
(同一个主题可以换模型对比,这是网关天然的优势)。

## 2. 存储:归档目录就是真相

改动之前,一张生成图存在两份,彼此不认识:

| | 位置 | 谁看得见 | 问题 |
|---|---|---|---|
| 前端 | IndexedDB(`utils/playgroundSession.ts`) | 用户 | 只属于这一个浏览器 |
| 后端 | `~/.tingly-box/image/YYYYMMDD/*.png + .txt` | 没人读 | 同一秒的两个请求互相覆盖;前端不知道它存在 |

工作台不能放在前端:tingly-box 常常不跑在本机,换个浏览器就没了。所以**工作台只存在
后端**,并且建立在已经在写的那份归档上,而不是另起一套存储:

```
~/.tingly-box/image/
  20260930/20260930-153012-a1b2c3.png   ← 图(id = 文件名去掉扩展名)
  20260930/20260930-153012-a1b2c3.txt   ← 给人看的 sidecar(格式沿用旧的)
  workbench/<12 位 hex>.json            ← 工作台:引用归档 id,不拥有文件
```

- 代码:`internal/vision/imagestore`(`Store` 读写归档,`Workbenches` 管工作台文件)。
- 不缓存:列表每次扫目录,用户手动丢进 / 删掉的文件下一次读就能看到。
- id 带随机后缀,修掉了"同一秒覆盖"。旧文件名(`YYYYMMDD-HHMMSS[-N]`)照样能列出来。
- id 先过正则再拼路径,不可能走出 image 目录。
- 工作台只引用 id:删工作台不删图;同一张图可以在两个工作台里。
- 删除一张作为某工作台根图的图会被拒绝(409):工作台不能聚焦在"什么都没有"上。删除
  衍生图则把它的子节点挂到它的父节点上,衍生关系始终是一棵树。

### 网关如何把"屏幕上这张图"和"磁盘上这个文件"对上

网关仍然尽力而为地落盘(`protocolserver.persistImages`),并在响应头里回报每张图的 id:

```
X-Tingly-Image-Ids: <id0>,<id1>,...      ← 与 data[] 顺序对齐,没存的位置为空
```

响应体保持 OpenAI 的形状不变,其他客户端忽略这个头即可。桌面端是跨源的,所以同时带上
`Access-Control-Expose-Headers`。

## 3. 控制面 API(`/api/v1/imagegen`)

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/images?limit&before` | 归档列表,按时间倒序,`next_before` 翻页 |
| POST | `/images` | 导入一张图(base64 / data URL),用来从非生成的图开工作台 |
| GET | `/images/:id`、`/images/:id/file` | 元数据 / PNG 本身(`<img>` 带不了 token,前端取 blob) |
| DELETE | `/images/:id` | 删图;是根图时 409 |
| GET/POST | `/workbenches` | 列表 / 新建(`root_image_id` 必须已归档) |
| GET/PUT/DELETE | `/workbenches/:id` | 读 / 改名称描述 / 删(图保留) |
| POST | `/workbenches/:id/items` | 记录衍生图(父节点不在本工作台里时记为根图) |
| DELETE | `/workbenches/:id/items/:image_id` | 从工作台移出(图保留) |

## 4. Playground 里的行为

- **入口在图上,不在设置里**:任意一张图的灯箱里有 "Focus on this image"。名称和描述默认
  从这张图来(名称取 prompt 首行,描述取 prompt),所以通常一键即可。还没归档的图
  (导入的、URL 结果)会先导入归档。
- **没有工作台时不渲染任何东西**(ux §9 降噪)。有工作台但没聚焦时,只有一个切换下拉框。
- **聚焦 = 把根图放进参考图**。切换到另一个工作台时,上一个工作台放进来的图会被移出;
  退出聚焦不改动请求。
- **描述放在 prompt 前面一起发送**,输入框下面写明了这一点;run 卡片上显示的就是实际发出
  的完整 prompt,没有看不见的拼接(ux §5)。
- **衍生关系**:结果的父节点 = 第一张来自本工作台的参考图,否则就是根图。点击工作台里的
  任何一张图,就把它(连同 id)放进参考图,所以"从第 3 张继续改"会被正确记成它的子节点。
- 从工作台里出的图再开新工作台时,默认描述用原工作台的描述、名称用这次的 prompt,而不是
  把一个工作台的描述套进下一个。
- 当前聚焦的是哪个工作台,存在 `localStorage`(只是这个浏览器的偏好);工作台本身一律从
  后端读。

## 5. 还没做 / 待定

- **通用 Playground 历史仍在 IndexedDB**。下一步是让它也从归档读,前端那份降为显示缓存,
  这样"两份数据"才算真正收敛成一份。
- **外部调用方的图也会被归档**(这是改动之前就有的行为)。要保留,就应该在 Image 页给出
  可见的历史与清理入口;要取消,就改成只在工作台里落盘。还没定。
- **URL 形式的结果**(部分 DashScope / MiniMax 模式)网关不落盘,这类图在工作台里没有 id,
  不会被记为衍生图。要支持就得在网关侧当场下载;URL 往往会过期,这件事本身就值得做。
- **Responses API 的 image_generation 路径**不经过 `persistImages`,不落盘。
- 多角度参考图、三视图、姿势库与工作台的结合,等最小形态用起来以后再看。
