# ImBot 输出铅笔画 — ASCII mockups of the predicted message flow

> 配套文档：`.design/imbot-output.md`（文字版分析 + 代码依据）。这份文档只做一件事——把那份分析里描述的消息序列画成文本框线图，方便直接"看"出来现在会是什么样子，而不是靠脑补。**不是真实截图**，是按代码逐条还原的示意；气泡文案、按钮文案都和实际发送的字符串一致（见 `imbot-output.md` 引用的代码行）。

## 场景设定

所有下面的画都用同一个最小场景，和 `imbot-output.md` §3 一致：

- 用户发：`@cc 把 foo.go 里的错误处理改一下`
- 这一轮触发了 1 次权限确认（`Edit` 工具）+ 1 次工具调用
- 用户点了"允许"

## 图例

```
🤖 = 机器人头像/消息来源       ⚠️N = 对应 imbot-output.md 里编号的问题点
──▶ = "用户做了个动作之后"     [......] = 按钮
```

## 平台原型 A：Telegram（🟢 支持原地编辑，体验最好的一档）

Feishu 的权限卡片部分和这个几乎一样（都实现了 `Restate`），差别只在按钮渲染成"卡片"而不是"inline keyboard"，其余消息序列完全相同——所以下面只画 Telegram 一份，Feishu 见"平台差异速查表"。

## 平台原型 D：DingTalk（🔴 无按钮能力，权限确认退化成文字）

Weixin、WeCom、WhatsApp 是同一个类别——`SupportsInteraction()` 全部为 `false`，权限/多选题一律走"编号列表 + 文字回复"这条路，画一份就够代表这四个平台。Weixin 目前额外被 `SuppressVerbose` 强制关掉了详细过程（见下方备注），所以它的真实序列会比这张图更短。

```
┌───────────────────────────────────────────┐
│ 🤖 my-bot                                  │
├───────────────────────────────────────────┤
│  ⏳ CC: Processing new session...           │  ← 消息①
│  ───────────────  💬 @cc  📁 my-project    │
│                                             │
│  ┌───────────────────────────────────┐    │
│  │ 🔐 Tool Permission Request          │    │  ← 消息②：没有按钮，
│  │ Tool: `Edit`                        │    │     整段是纯文字
│  │                                      │    │
│  │ 回复以下内容之一：                   │    │  ⚠️4
│  │  • y  - 允许                        │    │
│  │  • n  - 拒绝                        │    │
│  │  • a  - 总是允许                    │    │
│  └───────────────────────────────────┘    │
│                                             │
│                          用户输入 "y" ──▶  │
│                                     ┌────┐  │
│                                     │ y  │  │
│                                     └────┘  │
│                                             │
│  ┌───────────────────────────────────┐    │
│  │ ✅ Allow · for tool: `Edit`         │    │  ← 消息③（这里原本的“弹窗”
│  └───────────────────────────────────┘    │    消息②本来就没法收起/改写，
│                                             │    所以体验上没有 Discord 那种
│  ( 后面④⑤⑥⑦ 和前面一样 )                  │    "按钮残留"，但要求用户手打
│                                             │    指令本身就是更重的交互)
└───────────────────────────────────────────┘
```

## 平台差异速查表（对应上面四份画）

| 属于哪种画法 | 平台 | 权限提示形式 | 用完后会怎样 |
|---|---|---|---|
| 画 A（Telegram） | Telegram | 气泡 + inline 按钮 | 原地改写，按钮消失 |
| 画 A（同序列，UI 皮肤不同） | Feishu | 见画 C（卡片皮肤） | 卡片 patch，按钮消失 |
| 画 B（Discord） | Discord / Slack | 气泡/消息行 + 按钮 | **按钮永久留在记录里，还能再点** |
| 画 B（同问题，未接 Restate） | Lark | 声明了卡片能力，但没接 `Restate` | 同 Discord——和"亲兄弟"Feishu 体验不一致 |
| 画 D（DingTalk） | DingTalk / WeCom / WhatsApp | 纯文字编号列表，要求手打回复 | 没有按钮残留问题，但每次都要打字 |
| 画 D（更短） | Weixin | 同 DingTalk 的文字降级，**且已被 `SuppressVerbose` 强制静音**，实际只会看到①②③⑦，中间的工具聚合/详细过程不会发 | 四条消息里最"干净"的一档，是唯一被专门治理过的平台 |

## Before / After：如果要精简，大致会变成什么样（讨论稿，非定案）

只画 Telegram 这一个平台做示意——用来说明"如果做 `.design/imbot-output.md` §7 里提的第 1、2、3 条优化，视觉上会差多少"，不代表最终会这么改。

```
  现状（7 条消息）                    一种可能的精简版（3 条消息）
┌─────────────────────┐          ┌─────────────────────┐
│ ⏳ Processing...      │          │ 🔐 权限确认           │
│ ─────── 💬 @cc 📁      │          │ Tool: Edit            │
├─────────────────────┤          │  [✅][❌][🔄]          │
│ 🔐 权限确认(带按钮)    │          ├─────────────────────┤
├─────────────────────┤          │ ✅ 已同意              │
│ 🔐 权限确认✅已同意     │◀ 原地改写  │ 🔧 Edit foo.go · ok    │  ← 原地改写：
├─────────────────────┤          │                        │    权限卡片直接
│ ✅ Allow·for tool ⚠️1 │◀ 去掉      │                        │    变成结果卡片，
├─────────────────────┤          │                        │    不再单独发
│ 🔧 2 tool call(s)     │          ├─────────────────────┤
├─────────────────────┤          │ 已经把 foo.go 的错误处   │
│ 已经改好了，测试通过    │          │ 理改好了，测试通过。      │
├─────────────────────┤          │ ✅ 完成 · 4.2s · $0.014 │  ← Cost/Duration
│ [RESULT] SUCCESS ⚠️2  │◀ 折叠进回答 │ [🗑][📁][🔧]           │    折成回答尾部
├─────────────────────┤          └─────────────────────┘    一行小字，而不是
│ ✅ Task done + footer  │◀ 去掉重复                            独立一条消息
│  [🗑][📁][🔧]          │  footer
└─────────────────────┘
```

对应 `.design/imbot-output.md` §7：① = 去掉重复确认消息，② = `[RESULT]` 折叠成回答尾部的一行小字（而不是独立方括号调试块），③ = Processing 横幅与 Task-done 卡片合并成一条会被原地改写的消息。三个改动叠加，Telegram 上从 7 条降到 3 条；不支持编辑的平台（Discord 等）因为没有"原地改写"这个能力，降到的是 4 条（少了①③的合并收益，但仍然去掉①②两处冗余）。

## 问题点速查（对应画里的 ⚠️ 编号）

1. **⚠️1 重复确认**：`✅ Allow · for tool: \`Edit\`` 这条消息和"权限卡片被改写成✅ Approved"是两处完全独立的代码（`prompt_reply.go` 的 `send(...)` 和 `imprompter.go` 的 `editPromptToResult`），**所有平台都会重复发**，包括体验最好的 Telegram/Feishu。
2. **⚠️2 调试风格的 `[RESULT]` 块**：`[SYSTEM]` `[RESULT]` 这种方括号标签是给人调试用的格式，直接进了聊天窗口；且这条消息**不受 quiet 模式过滤**，关了 verbose 也照样发。
3. **⚠️3 按钮永久残留**：Discord / Slack / Lark / DingTalk / Weixin / WeCom / WhatsApp 都没实现 `imbot.MessageRestater`，权限按钮发出后就是"死"的，但视觉上和"还能点"的按钮长得一模一样。
4. **⚠️4 文字降级**：DingTalk / Weixin / WeCom / WhatsApp 没有按钮能力，权限确认和多选题一律退化成"编号列表 + 手打回复"，比按钮更占屏幕、也更麻烦。

详细代码依据见 `.design/imbot-output.md` 对应章节。
