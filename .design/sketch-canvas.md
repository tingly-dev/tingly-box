# Sketch Canvas(生图 Playground 的手绘草图输入)

> 适用对象:tingly-box 前端贡献者。
> 描述 Image Playground 的手绘草图能力:在画布上画一张简图,作为参考图像
> 走 edit 链路生成。
> 关联文档:`ux-principles.md`(判断标准)、`imageedit.md`(edit 网关链路)、
> `image-slice.md`(同一 Playground 的后置切分)。

---

## 1. 背景

Playground 已经支持上传/拖拽/粘贴参考图,但有一类很常见的起点没有覆盖:用户脑
子里有个构图,手边没有图。之前的做法是去别的工具画一张、存文件、再回来上
传——三次跳转只为了一张"大概这样"的草图。

这个功能把画布直接放进 Playground:画完即成为参考图,prompt 说它该变成什么。

---

## 2. 核心决策

### 2.1 草图是参考图的一种来源,不是第三种模式

最初的备选是加一个 `Sketch` 模式。**否决**,理由:

- 草图与上传图在下游完全同构:同一个 `ReferenceImage` 列表、同一个请求、同一
  张历史卡片。给它单独开一个模式,是把"图从哪来"和"要做什么"两条正交轴拧到
  一个旋钮上(原则 4)。
- 混用是真实需求:一张产品照片 + 一张手画的构图示意,一起发给模型。分模式
  会把这种组合直接堵死。

这个判断后来推进了一步:Playground 原有的 Generate / Edit 模式切换也被拆掉了
(见 `imageedit.md` §6),参考图区永远存在、可选,端点按参考图数量推导。草图
入口因此不再需要先切模式。参考图的三种来源 **Browse / Paste / Sketch** 作为平
级动作并排呈现:空状态是虚线框里的三个文字按钮,已有图时是缩略图后面的三个
同样大小的方块(拖拽没有按钮,虚线框本身就是投放目标)。第一版把 Sketch 做成
了嵌在提示文字里的一个独立按钮,看起来像个外来物——来源之间没有主次,就不该
有一个长得不一样。`ReferenceImage` 多一个 `source: 'upload' | 'sketch'`
字段,除此之外提交链路零改动。

### 2.2 画布尺寸跟随 `Size`,而不是再选一次

画布的 backing store 直接取 Playground 当前的输出尺寸(`1024x1792` →
1024×1792 的画布),标题栏把具体像素写出来(`1024 × 1792 px · matches Size`,
原则 5)。用户不需要在对话框里再回答一次"多大、什么比例":模型收到的参考图
和它被要求输出的形状天然一致,不会出现草图是方的、结果被裁成竖的这种意外。

尺寸在打开时读一次。中途改 `Size` 需要重采样已有笔迹,对话框本身生命周期
很短,关掉重开是更诚实的答案。

### 2.3 白底不透明,橡皮擦即"刷白"

画布永远是不透明白底,不做透明/有底的开关(原则 6)。透明草图对大多数图像模
型是含糊的输入——线条之外什么都没有,模型不知道该把它当白纸还是当蒙版。既然
底是白的,橡皮擦就是画白色,比画笔宽一档(擦是粗动作)。这样只有一条绘制路
径,没有 `destination-out` 合成模式的分支。

### 2.4 固定小调色板,不做取色器

六个色:黑做轮廓,加五个模型能叫得出名字的纯色("把红色的圈改成太阳")。
取色器是一个用户没来这里做的决定;草图的信息量在形状,不在色号。

### 2.5 可再进入

草图缩略图右下角有画笔按钮,点开是同一个画布,已有笔迹作为底图加载进来继续
画,提交时**原位替换**(保持它在参考图列表中的位置)。"用了"不等于"锁死"
(原则 10)。这也是 `source` 字段存在的唯一理由:上传图没有这个入口。

### 2.6 prompt 的教育随场景切换

参考图里一旦有草图,prompt 的 placeholder 从"描述你想做的修改"换成"描述这张
草图应该变成什么"——草图和改图是两种心智,提示语跟着变(原则 8),但不替用户
写 prompt(与 `image-slice.md` §2 同一条原则:prompt 是用户的东西)。

## 3. 实现要点(`SketchCanvasDialog` + `utils/sketchCanvas.ts`)

| 事项 | 做法 |
|------|------|
| 绘制 | Pointer Events(鼠标/触屏/笔一套代码),`setPointerCapture` 保证拖出画布不断笔;`getCoalescedEvents` 取浏览器合并掉的中间采样点,快速笔画是曲线不是折线;`touch-action: none` 防止手机把手势当滚动 |
| 坐标 | CSS 盒子按 `fitWithin` 等比缩到对话框内,永不放大超过 backing store;`toCanvasPoint` 把视口坐标映射回 backing store |
| 笔宽 | 相对 1024 画布定义,按 `max(w,h)/1024` 缩放,同一档在 512 和 1792 上视觉粗细一致 |
| 撤销 | 每笔落笔前 `getImageData` 快照压栈(`StrokeHistory`,上限 30),撤销即 `putImageData`;`Ctrl/Cmd+Z` 绑定在对话框打开期间 |
| 导出 | `canvas.toBlob('image/png')` → `File`(`sketch-<ts>.png`),预览用 `toDataURL`,与上传图共用同一种 data URL 表示 |
| 挂载时机 | MUI Dialog 通过 Portal 延后一拍挂载子树,`[open]` effect 跑的时候普通 `ref` 还是 `null`。canvas 和舞台容器改用 callback ref → state,effect 在节点真正存在后再跑一次。这个坑第一版踩过:画布区域是空的、按钮永远 disabled |

纯逻辑(尺寸解析、fit、坐标映射、笔宽、撤销栈)全部在 `utils/sketchCanvas.ts`,
有单测;组件只是这些 helper 加 2D context 调用的薄壳。

## 4. 人形(可摆姿势的人偶)

### 4.1 为什么它是画布里的一个工具,不是第四种参考图来源

"人形布局"想解决的是文字 prompt 最控制不住的一件事:姿势和景别。但我们的出图
链路(OpenAI 兼容 generations/edits + Codex 原生 images)**没有任何一条支持 pose
条件输入**,ControlNet 这类东西根本递不进去。所以一个人形在我们这里只可能是
"参考图里的像素"——而那恰好就是草图。

于是结论和 §2.1 是同一条:不给它开新入口。Browse / Paste / Sketch 三个来源不变,
人形是 Sketch 对话框里紧挨着 Pen / Eraser 的第三个工具。它改变的是"怎么起笔",
不是"图从哪来"。同理,场景布局不做成独立编辑器——它要的是矩形/箭头/文字,属于
§5 里的画布工具,做完那三样这个需求自然消失。

### 4.2 画成木头关节人偶,不是火柴人

线条火柴人有一个具体的失败模式:模型把它**照着画进结果里**。实心人偶读起来是
"一个摆着这个姿势的身体",不是需要复现的线稿。

形体照美术用的木头关节人偶来:蛋形头 + 颈栓,胸廓和骨盆是**两个分开的体块**、
中间一颗腰球,肩肘腕髋膝踝是看得见的关节球,四肢是两头粗细不同的锥段,手是连着
小臂的连指块,脚是横在小腿末端的块。这不是装饰——**胸廓的横轴挂在肩线上,骨盆
挂在髋线上**,所以拖一侧肩膀只有胸廓跟着转,骨盆不动,躯干因此有了扭转和正背面。
一排等宽胶囊给不了这个信息,而姿势参考图里最值钱的恰恰是它。

体块各自旋转带来一个必须处理的退化情形:把肩膀往下拽很远时,胸廓会从脖子底下
转出去、露出缝。所以躯干底下永远先画一根 neck→髋中点的锥形"脊柱",人偶在任何
关节角度下都是连着的。

配色三档(躯干 / 关节球更深 / 头更浅),不做渐变也不用木头棕:姿势才是信息,
真木纹反而在邀请模型画一个木头娃娃。只提供这一种画法,没有开关(原则 6);
如果某个 provider 仍然照抄人偶,该调的是这里的渲染,不是把选择推给用户。

同样地,**不替用户往 prompt 里塞"以骨架为姿势参考"这类句子**——`image-slice.md`
§2 已经定过这条线:prompt 是用户的东西。产品这边只把教育换掉:画布上有人形时,
底部提示语变成"灰色人偶只是姿势参考,他是谁、穿什么由提示词来说"(原则 8)。

几何全部从那 15 个关节推导(`figureParts`),**没有额外的手柄**:结构变好看不
以增加用户要操作的东西为代价。

### 4.2.1 为什么不用现成方案

调研过两个:

| 方案 | 结论 |
|------|------|
| [mannequin.js](https://github.com/boytchev/mannequin.js/)(three.js 关节人偶库) | 形态最接近,但 **GPL-3.0**。本仓库是 MPL-2.0 + 商业双授权,引入会污染商业授权那条线。否决。 |
| [open-pose-editor](https://github.com/ZhUyU1997/open-pose-editor)(3D OpenPose 编辑器) | MIT,three.js,但产出是 OpenPose 骨架 / depth / normal / canny——**全是 ControlNet 的输入**,我们的 provider 一个都收不到;而且它是一个完整应用,不是库。 |

真要上 3D(能拿到透视缩短和机位,2D 拖关节永远给不了),只能自己拿 three.js
加一个自有模型。**先不做**:模型到底吃不吃姿势参考还没验证,3D 是一种昂贵得多的
失败方式。等 2D 版被证明"方向对但表达力不够"再说。

### 4.3 交互

选中人形工具时,画布是空的就**直接落一个站姿人偶**,不先问姿势(原则 2)。
姿势预设(站/走/坐/举手)只在选中某个人偶之后才出现在工具栏里,作用是**就地
换姿势**——保持位置和大小,只换关节(原则 10)。

| 动作 | 手势 |
|------|------|
| 摆姿势 | 拖关节 |
| 移动 | 拖身体(命中任意骨骼或头部) |
| 缩放 | 拖右下角方形手柄,绕人偶中心等比缩放,有下限防止缩成抓不住的点 |
| 镜像 / 删除 | 工具栏按钮;删除也可用 Delete/Backspace(输入框内不抢键) |

命中优先级是关节 → 缩放手柄 → 身体 → 空白处取消选中;多个人偶时后画的在上面。
点一下只是选中,**不产生 undo 步**:快照在第一次 pointermove 时才入栈。

### 4.4 分层与 undo

人偶是**对象**,不是像素:笔迹画在底层 canvas,人偶画在覆盖其上的 overlay canvas,
只要对话框还开着就能继续调。overlay 只在人形工具激活时接收指针事件
(`pointerEvents`),所以在人偶上画画不需要先切模式。蓝色关节手柄只画在 overlay,
提交时另起一张 canvas 合成"底图 + 人偶",**手柄永远不会进入发给模型的 PNG**。

undo 只有一条栈:笔迹快照 `ImageData`、人偶编辑快照人偶数组、清空两者都存,
每帧还记住当时的 rasterDirty,所以 Ctrl+Z 永远等于"我刚才做的那一步",
不管是哪个工具做的。

提交时人偶被烧进 PNG——再进入(§2.5)拿到的是像素,姿势不再可调。这是有意的:
`ReferenceImage` 只承载文件和预览,为了让人偶跨对话框存活而把关节数组挂到参考图
上,是让数据结构去迁就一个短生命周期的编辑态。

代码:纯几何(预设、包围盒、平移/缩放/镜像、命中测试)在 `utils/poseFigure.ts`,
有单测;canvas 绘制在同文件末尾;交互在 `SketchCanvasDialog`。

## 5. 未做 / 后续

- **在已有图片上标注**(圈出要改的区域):技术上就是把上传图作为 `initialImage`
  打开画布,链路已经通了;没做是因为它和 edit 的 `mask` 语义有重叠,而 Codex
  原生协议不支持 mask(见 `imageedit.md` §3.3),先不引入一个多数 provider 收不
  到的输入。
- **矩形 / 箭头 / 文字**:这三样就是"场景布局"的实际需求(沙发在这、窗在那),
  比一个独立的布局编辑器更小也更通用;独立编辑器还多一个问题——块上的标签文字
  容易被模型直接画进成品图。优先级排在人形之后。
- 压感:草图的目的是"大概这样",先不做。
- 人形的后续:多人时的前后遮挡关系、有朝向的头(眼睛朝哪)、以及 §4.2.1 里那条
  3D 路线。都要等实际用下来确认模型确实吃这一套之后再说。
