# Sketch Canvas(生图 Playground 的草图与人偶输入)

> 适用对象:tingly-box 前端贡献者。
> 描述 Image Playground 的草图能力:在画布上画一张简图、摆一个人偶,作为参考
> 图像走 edit 链路生成。
> 关联文档:`ux-principles.md`(判断标准)、`mannequin-standard.md`(人偶的画法基准)、
> `imageedit.md`(edit 网关链路)、
> `image-slice.md`(同一 Playground 的后置切分)。

---

## 1. 背景

Playground 已经支持上传/拖拽/粘贴参考图,但有一类很常见的起点没有覆盖:用户脑
子里有个构图,手边没有图。之前的做法是去别的工具画一张、存文件、再回来上
传——三次跳转只为了一张"大概这样"的草图。

这个功能把画布直接放进 Playground:画完即成为参考图,prompt 说它该变成什么。
后来又补了人偶(§4),因为姿势和景别是文字 prompt 最控制不住的东西,而我们的出图
链路收不到任何姿势条件输入,能给模型的只有"参考图里的像素"——那恰好就是草图。

---

## 2. 核心决策

### 2.1 草图是参考图的一种来源,不是第三种模式

最初的备选是加一个 `Sketch` 模式。**否决**,理由:

- 草图与上传图在下游完全同构:同一个 `ReferenceImage` 列表、同一个请求、同一
  张历史卡片。给它单独开一个模式,是把"图从哪来"和"要做什么"两条正交轴拧到
  一个旋钮上(原则 4)。
- 混用是真实需求:一张产品照片 + 一张手画的构图示意,一起发给模型。分模式
  会把这种组合直接堵死。

这个判断后来推进了一步:Playground 原有的 Generate / Edit 模式切换也被拆掉了
(见 `imageedit.md` §6),参考图区永远存在、可选,端点按参考图数量推导。草图
入口因此不再需要先切模式。参考图的三种来源 **Browse / Paste / Sketch** 作为平
级动作并排呈现:空状态是虚线框里的三个文字按钮,已有图时是缩略图后面的三个
同样大小的方块(拖拽没有按钮,虚线框本身就是投放目标)。第一版把 Sketch 做成
了嵌在提示文字里的一个独立按钮,看起来像个外来物——来源之间没有主次,就不该
有一个长得不一样。`ReferenceImage` 多一个 `source: 'upload' | 'sketch'`
字段,除此之外提交链路零改动。

这条后来又挡住了一次扩张:人偶该不该做成第四种来源。不该,理由同上(§4.1)。

### 2.2 画布尺寸跟随 `Size`,而不是再选一次

画布的 backing store 直接取 Playground 当前的输出尺寸(`1024x1792` →
1024×1792 的画布),标题栏把具体像素写出来(`1024 × 1792 px · matches Size`,
原则 5)。用户不需要在对话框里再回答一次"多大、什么比例":模型收到的参考图
和它被要求输出的形状天然一致,不会出现草图是方的、结果被裁成竖的这种意外。

尺寸在打开时读一次,中途改 `Size` 要关掉重开。这条**现在是可以取消的将就**:
笔迹和人偶都已经是数据而不是像素(§3),按新尺寸重绘不再需要重采样。留着只是
因为还没做。

### 2.3 白底不透明,橡皮擦即"刷白"

画布永远是不透明白底,不做透明/有底的开关(原则 6)。透明草图对大多数图像模
型是含糊的输入——线条之外什么都没有,模型不知道该把它当白纸还是当蒙版。既然
底是白的,橡皮擦就是画白色,比画笔宽一档(擦是粗动作)。这样只有一条绘制路
径,没有 `destination-out` 合成模式的分支——这条便宜后来又收了一次利息:笔迹
改成矢量重放时,橡皮不需要任何特例(§3.2)。

### 2.4 固定小调色板,不做取色器

六个色:黑做轮廓,加五个模型能叫得出名字的纯色("把红色的圈改成太阳")。
取色器是一个用户没来这里做的决定;草图的信息量在形状,不在色号。

### 2.5 可再进入,而且是真的可再编辑

草图缩略图右下角有画笔按钮,点开是同一个画布,**原来的笔迹和人偶原样回来**,
提交时原位替换(保持它在参考图列表中的位置)。"用了"不等于"锁死"(原则 10)。
这也是 `source` 字段存在的唯一理由:上传图没有这个入口。

第一版的"可再进入"只做到一半:提交时一切被压平成 PNG,重开拿到的是像素,姿势
不再可调、撤销也断在保存那一刻。修法见 §3.3——那是本文档里唯一一次**推翻自己
先前的判断**,值得单独记。

### 2.6 prompt 的教育随场景切换

参考图里一旦有草图,prompt 的 placeholder 从"描述你想做的修改"换成"描述这张
草图应该变成什么"——草图和改图是两种心智,提示语跟着变(原则 8),但不替用户
写 prompt(与 `image-slice.md` §2 同一条原则:prompt 是用户的东西)。

画布上有人偶时,底部提示语同样换成"灰色人偶只是姿势参考,他是谁、穿什么由提示
词来说"。**不往 prompt 里塞"以骨架为姿势参考"这类句子**,哪怕那样成功率更高。

## 3. 画面是三层数据,不是一张位图

这是整个模块最核心的结构,人偶、撤销、再编辑三件事都从它长出来。

```text
backdrop   旧版压平的草图才有,一张底图                    ← 通常为空
strokes[]  每一笔:点串 + 颜色 + 粗细 + 笔/橡皮            ← 底层 canvas
figures[]  每个人偶:15 个关节 + 明度档位                  ← overlay canvas
```

底层 canvas 画笔迹,overlay canvas 画人偶,只要对话框开着,两层都还是数据。
overlay 只在人形工具激活时接收指针事件(`pointerEvents`),所以在人偶上继续画画
不需要先切模式。蓝色关节手柄只画在 overlay。

### 3.1 提交 = 合成,但原料一起交出去

```text
SketchResult {
  file, previewUrl,                 ← 发给模型的合成 PNG(含人偶,不含手柄)
  layers: { strokes, figures, backdrop }
}
```

合成走另起的一张 canvas,所以**手柄永远不会进入发给模型的 PNG**,而活的画布
保持分层。`ReferenceImage.layers` 收下 `layers`,**只服务编辑器**;请求链路仍然
只用 `file`,一行没改。

### 3.2 笔迹是点串,不是像素

一笔存的是它被画出来的那串点。画的时候仍然逐段直接画到 canvas 上(每次
pointermove 全量重绘看得见卡顿),**抬笔时这一笔才进列表**——一次手势 = 一个
undo 步,而且屏幕上已有的像素与重放的结果一致。

undo 只有一条栈,**每帧是整个画面状态**(笔画 + 人偶 + 底图),所以 Ctrl+Z 永远
等于"我刚才做的那一步",不管是哪个工具做的。之所以敢存整份而不是"只存被碰到的
那一层",正是因为两层都已经是列表:一帧只是两个数组引用 + 一个图片引用,而不是
1024² 的 `ImageData`(4 MB)。部分快照省不下什么,却要在撤销时把整份状态拼回来,
底图和图层因此走散过一次。

清空会把 backdrop 一起带走,否则"清空"之后画布会退回它打开时的那张图。

### 3.3 重开时把编辑态整个接回来

- 笔迹按列表重放,人偶回到对象层,**只有一个人偶时直接选中它**——手柄本身就是
  "这还能改"的回答,不该等用户先点一下才出现。
- **undo 历史用笔画列表反推**:第 i 帧就是前 i 笔。所以 Ctrl+Z 能一路撕掉保存
  之前画的笔画。人偶没法这样反推,它从保存时的姿势开始。
- 没有 `layers` 的草图(旧版本压平的)照常打开,当作可以继续画的底图,只是不再
  可摆、不再可逐笔撤销。

第一版把这些都压平了,理由是"不让 `ReferenceImage` 去迁就一个短生命周期的编辑
态"。**这个判断是错的**:摆姿势和画草图本来就是反复调的动作,一提交就锁死,等于
把原则 10 让给了数据结构的洁癖。代价也远比想象小——存的是数组,比第二张全尺寸
PNG 还省。

## 4. 人偶

### 4.1 它是画布里的一个工具,不是第四种参考图来源

我们的出图链路(OpenAI 兼容 generations/edits + Codex 原生 images)**没有任何一条
支持 pose 条件输入**,ControlNet 这类东西根本递不进去。所以一个人偶在我们这里
只可能是"参考图里的像素"——而那就是草图。结论和 §2.1 同一条:不开新入口,人偶是
Sketch 对话框里紧挨着 Pen / Eraser 的第三个工具。它改变的是"怎么起笔",不是
"图从哪来"。

同理,**场景布局不做成独立编辑器**——它要的是矩形/箭头/文字,属于 §6 里的画布
工具,做完那三样这个需求自然消失;而独立编辑器还多一个问题:块上的标签文字容易
被模型直接画进成品图。

### 4.2 画成木头关节人偶,不是火柴人——而且它有厚度

线条火柴人有一个具体的失败模式:模型把它**照着画进结果里**。实心人偶读起来是
"一个摆着这个姿势的身体",不是需要复现的线稿。

形体照美术用的木头关节人偶来,但**关键在"一个形体",不是"一堆体块"**。第一版把躯干
拆成胸椭圆 + 腰球 + 骨盆椭圆,每块各自打光——所有测试都过,看上去仍然是三个蛋摞着。
凸体块的并集永远会出卖自己的接缝,再怎么拼也拼不成一个身体。

现在躯干是**两块**:胸廓盾形(斜方肌 → 肩角 → 肋收 → 腰)和骨盆桶(窄口 → 髂嵴 →
收到髋关节),中间是**真的空隙**,腰球从里面露出来。中间那一版是一条闭合轮廓加一道
腰缝,形是整的但腰读不出来——**一条画在形体上的线是折痕,不是关节**。分块本身不是
罪,"三个蛋"的教训真正说的是:分成的必须是**有轮廓的形**,不是凸体块。
`CHEST_PROFILE` / `PELVIS_PROFILE` 两张表就是这两个形状。它仍然会拧转
——**轮廓的上缘挂在肩线上,下缘挂在髋线上**,中间插值,所以拖一侧肩膀躯干跟着转、
骨盆不动。

**关节必须落在身体的角上**,这一条返工过一次,而且是最贵的一次。为了让胯不比腰窄,
我一度把躯干宽度从关节那里往外撑(肩 ×1.29、胯 ×1.52),结果身体的边缘跑到了关节
外面:手臂成了从"肩台"底下挂出来的,腿从一条垂到髋关节下面的"裙子"中间伸出来——
正面看就是一条尿布,而且**十几个姿势一起变怪**。修法不是把身体吹大,是**把关节挪
出去**:肩关节放到三角肌外角、髋关节放到骨盆下外角,骨盆到髋关节就收口、不往下垂。
详见 `mannequin-standard.md` §2.5。

头同理。椭圆是一个蛋,蛋插在杆上是人偶最像玩具的地方,所以头也是一条轮廓——颅骨最宽、
到下巴收窄;脖子加粗成一根柱子,不再是一根看不见的栓,而且**向前倾 7°**:垂直的脖子
是一根桅杆,人的颈椎从来不垂直。

**四肢同样是闭合轮廓,关节处没有球。**这一条是被"球形关节画得不优雅"这句反馈逼出来
的,而去行业里看了一圈之后发现,问题不在球画得好不好,在于**球本身就不该有**:实体
木头人偶必须在关节处鼓出来才转得动,那是制造工艺,不是形体;画画的人(Proko 那一派的
"人偶化")在关节处是**收窄**的,因为关节是骨头交汇处、是转面,不是肉最多的地方。
照着制造工艺画,就是我们那一版读起来像玩具的原因。

这条规矩是对**铰链**说的,不是对**球窝**说的——真的木头人偶自己就给出了分界线:
肩和髋是**球**(球窝关节,球就是关节本身),肘、膝、腕、踝是**收窄**加一根销钉。
所以肩球和髋球留着(画在躯干下面,只露出肢体没盖住的那一牙),铰链上一个球都没有。
躯干在腰上也有一条细缝,对应木头人偶上胸块和骨盆块之间那道真实的缝。

所以一条肢体现在是一条从根到指尖的连续轮廓(`limbOutline`):沿各节点的角平分线两侧
偏移、两端各扣一个半圆帽。半径表直接写进 Proko 的三条规矩——上臂几乎不收(0.031 →
肘 0.028),小腿在**膝下三分之一处最粗**(膝 0.030 → 腓肠 0.034 → 踝 0.023),手和脚
是肢体的末端而不是贴上去的锭子。转折只用一条**横过肢体的细弧线**(seam)交代,那是
一个转面,不是一个圆点。

比例照 Loomis 八头身对齐:下巴 1、乳线 2、脐 3、耻骨 4(正中)、膝 6、脚底 8,肩宽约
两个头。这一轮的审计里只有一个常数是错的,而且错的方向和我自己先前的判断相反——头
偏**小**,不是偏大(缩头之后整个人变成 8.7 头身,那是时装画,不是人)。

肢体折回自己身上时(盘腿俯视,小腿掖在大腿下面)单条轮廓会自交,填出一片鳍。这时候
**在折点把肢体拆成两片、按深度排序**——画画的人在这里也是把小臂画在**上臂之上**,
而不是把两者揉成一个形。阈值取屏幕上的转角,不是关节的真实角度:正面看直挺挺的膝盖
可以在三维里弯得很厉害。

**第一版是平的,这是它真正的天花板。**平面人偶只能说"手臂指向左边",说不出"手臂
指向你";一条胳膊不能从身体前面横过去;躺着和蹲着只能靠把躯干在屏幕平面里扳倒来
假装。摆得再仔细,交给模型的仍然是一张剪纸。所以每个关节带一个 z,每个人偶有
**自己的一台透视相机**(§4.4)。

几何全部从关节 + 深度推导(`figureParts`),**缺省不加手柄**:结构变好看不以增加用户
要操作的东西为代价。唯一的例外是**第 16 个关节 `face`**——脸朝哪是身体唯一推不出来的
事("回头看"是一个姿势,不是一个细节),而手朝哪、脚尖朝哪跟着所属肢体走就够准,没人
会去拖第二次。曾经有过一个把手和脚也做成关节的"精细档",砍掉了:**没人会拖的关节是
没有用途的手柄**,五个就是噪声(原则 9)。

透视,不是正交:正交投影下的 3D 姿势看着还是平的。相机距离取 3.4 个 `figureUnit`,
近处明显变大、转过去的躯干明显缩短,又不至于变成鱼眼。**粗细随景深缩放,长度随投影**
——朝镜头伸出的大腿因此是"短而粗"的,而不是"细而长",这正是透视缩短的定义。

七条踩出来的渲染经验:

- **一个体块一盏灯,不是一个零件一盏灯。**每个零件各自打径向渐变,正是告诉眼睛"体块
  在这里"的东西。躯干现在整条轮廓吃同一道光,接缝自己就没了;四肢仍然逐段横向打光,
  因为一段肢体本来就是一根圆柱。
- **按体块分组、从后往前画。**六组:躯干、头颈、两臂、两腿。组内顺序由解剖决定,
  组间顺序由深度决定。这才有"近侧手臂盖住胸口"这种遮挡,而遮挡是深度最直接的证据。
- **rim 每组一遍,不是整个人偶一遍。**一遍拉平的 rim 会把横过胸口的手臂和胸口**焊成
  一块**,而那恰恰是近侧手臂唯一不能做的事。组内 rim 仍然是一次并集,所以一条胳膊
  自己的几段之间没有缝。多边形的外扩用"按两倍 rim 描边再填充"实现,是精确的偏移。
- **铰链上不要球。**肘、膝、踝上曾经各有一个球,它们比躯干深一整档,于是每一个都成了
  贴在肢体上的深色圆饼。调浅、调小都没用,因为**球画在铰链上本身就是错的**(见上)。
  肩球和髋球留着——那两个是球窝关节,球就是关节。
- **同一个球不要画两遍。**髋球属于躯干,画在骨盆**下面**,只在大腿接缝处露出一牙;
  跟着腿再画一遍就压在大腿上,读成一个长错位置的膝盖。这个 bug 藏了一版才被发现,
  因为它只在放大之后才明显——**难看的东西要放大了看,缩略图会替你遮丑**。
- **手臂的根要往里塞。**手臂自成一组,它的轮廓端帽如果正好扣在肩关节上,就会在肩线
  上顶出一个圆包。把根节点沿肢体方向推进 0.78 个半径,帽子就藏进躯干里去了;腿只推
  0.3,因为髋关节本来就深在骨盆内部。
- **人偶必须有正面。**木头人偶没有五官,于是背面视角和正面视角**逐像素相同**——
  那样"把他转过去"就是一个模型永远读不出来的控件。所以头上有一块**面部平面**:
  垂直于头骨自身的轴、朝向 `face` 关节,转过去就直接消失。它比头略亮而不是略暗:光在
  前方,脸是头上最迎光的那一面;而一块深色斑会被模型画成面具。
- **脚顺着身体朝向,不横在小腿末端。**平面时代这两者看不出区别;有了深度,一块横搭在
  脚踝上的板会让每个站姿都变成内八字。取"身体正前方去掉小腿分量"的方向,所以抬起的腿
  会把脚一起带过去,而朝镜头走来的人不会长出一对滑雪板(投影长度就是缩短量)。

配色三档(躯干 / 球窝更深 / 头更浅),中性灰,不用木色:木色只会邀请模型画一个
木头娃娃。只提供这一种画法,没有开关(原则 6);如果某个 provider 仍然照抄人偶,
该调的是这里的渲染,不是把选择推给用户。

### 4.3 骨架:关节有父子,骨长不变——在三维里

根在髋中点,髋→左右髋→膝→踝,髋→颈→左右肩→肘→腕,颈→头。拖一个关节是让它
**绕父关节转**、并带着整条子链刚性跟随(罗德里格斯公式,绕两个方向的叉积轴),
所以骨长永远不变。少数需要怪比例的情况按住 Alt,退回单点拖拽(在它原本的深度上)。

关键的一条:**屏幕上的一个点,对应的是关节在三维里的一整圈位置,不是一个位置。**
把肘拖到上臂投影长度的一半处,剩下的那一半只能指向屏幕外——这是唯一保长的解释。
于是:

- 指针落在骨头的"球"之内 → 差额全部换成深度,**透视缩短是拖出来的,不是另开一个控件**;
- 指针落到球的轮廓之外 → 骨头躺回画面平面,直接指向指针,和平面时代一模一样;
- 默认留在肢体当前所在的那一侧(半球),**按住 Shift 送到身体背面**。歧义是真实存在的,
  给它一个键,而不是给它一个模式。

### 4.4 机位:转身是相机,不是姿势

2D 版给不了机位,这是它和"立体"之间差的第二样东西(第一样是透视缩短)。现在每个
人偶自己带一台相机:**左下角一个圆环手柄**,横拖转身、竖拖抬降机位——右下角那个
方块手柄是缩放,两个都是"对整个身体做的事",就用同一类控件,而不是进一个模式。

- **关节是唯一事实来源,`turn` 只是已经施加在关节上的那个旋转的备忘。**每次改动都从
  *总角度*重新推导关节(先 yaw 后 pitch,顺序固定),而不是把增量一帧一帧乘上去:
  增量累积会慢慢把 roll 揉进身体里,一个无缘无故侧倾的人偶读起来是坏掉,不是摆好。
- **相机瞄准躯干中点(颈-髋),不是关节包围盒的中心。**包围盒随任何一条肢体移动,
  瞄着它意味着拖一下手腕,整个人会被重新投影、肉眼可见地挪一下。
- yaw 可以转满一圈(背面是合法参考),pitch 夹在 ±78°:再多就是顺着人自己的轴看
  下去,没有东西可读了。
- **视角是独立控件,不是姿势库里的更多条目**(原则 4)。同一个身体从侧面看还是同一个
  身体;把机位折进姿势列表,意味着点"坐下"会顺手把模型转个身。工具栏上那颗按钮的
  文字**就是角度本身**(`35° / 8°`),既是标签也是读数(原则 5);展开是六个常用
  机位,每一格画的是**这个人偶**在那个角度下的样子,不是一个相机图标。
- 镜像会把 yaw 取反:把一个朝左转 35° 的人镜像过来,他就是朝右转 35°,读数必须跟上。

### 4.5 姿势库

四个预设按钮撑不到三十几个姿势,所以工具栏上只留一个 **Poses**,点开是分组的
缩略图网格(站姿 / 动作 / 坐蹲 / 躺卧 / 手势,36 个),点一个就地换姿势。

- **姿势用角度声明,不写坐标。**一根骨头是一个数或两个数:`-50` 是它在屏幕平面里的
  角度(0 朝下、+90 朝右、±180 朝上),`[-50, 30]` 表示同一根骨头再朝镜头**抬起 30°**
  (负数压到身体背面)。把深度写成第二个数而不是第二张表,好处是原来写对的平面姿势
  一个字都不用改,而"上臂 -50、朝镜头 30"仍然是脑子里能想象的东西。躯干另有
  `lean`(屏幕平面内倾)/ `bend`(朝镜头折)/ `twist`(肩相对髋的拧转)。
- **所有姿势共用一套骨长**,并且是**三维骨长**。这是硬要求:拖拽本身保的就是三维骨长,
  库里的姿势若各自骨长不同,换一个姿势就会悄悄改变这个人的身材。单测直接断言了这条——
  注意断言必须量三维,一条被缩短的肢体在屏幕上**本来就该**量出来更短。
- **归一化用同一个缩放**,而不是"把每个姿势拉满整个盒子":蹲着的人本来就比站着的矮。
  换姿势时对齐的是**躯干骨长**而不是包围盒高度,同理;机位也一并保留(§4.4)。
- **缩略图就是同一个渲染器画的**,并且**按人偶当前的机位画**。姿势库唯一的价值是
  "点到的就是拿到的";一个正面朝你的人,他的鞠躬缩略图就该是那个压扁的样子。
- 缩略图等比缩放到格子里,**但绝不放大超过站姿在同一格里的大小**。一切粗细都以
  `figureUnit` 为单位,把一个蹲姿放大到填满格子会让它比旁边的站姿粗 40%——一张
  每格身材都不一样的网格,读起来是三十个人,不是一个人的三十个姿势。

角度是可以在脑子里想象,但想象会错:第一版的跑步手臂折在胸前、蹲是往后坐、鞠躬和
伸手的躯干朝向反了。**改姿势就把全部渲染成一张对照表看**,比单看一个快得多;三维化
这一轮的脚朝向、胸廓变气球、缩略图放大失真,全都是在对照表上一眼看出来的。

### 4.6 多个人偶

一个画面里放两三个人是常见需求(对话、合影、人群),所以多人偶要能用,不是能存在:

- **落点**:新人偶从画布中心向外找第一个空位,不叠在已有的人身上。全占满了就级联
  偏移,至少保证抓得到。
- **明度**:同一个灰的两个人偶一旦交叠就糊成一坨,模型连画面里有几个人都读不出来。
  所以人偶有三档明度,**创建时定死、存进数据**——按列表位置上色的话,删掉一个会让
  其余的集体变色。只调明度不换色相,它们仍然是同一种材质。
- **叠放时的选中**:点一摞人偶是**往下走**,不是永远选最上面那个,否则底下的永远
  够不着。选中态的冷色调覆盖在明度之上,所以"选中的是哪个"任何时候都清楚。

### 4.7 手柄:能不能抓得住,是可以量的

"感觉不好控制"这种反馈没法直接修,所以先把它变成数字:遍历 36 个预设 × 6 个视角
=216 个组合,量**任意两个手柄在屏幕上的最近距离**,和拾取半径(≈18 canvas px)比。

原始状态:**53%** 的组合里至少有一对手柄近到分不开,41 个组合里有两个手柄挨在半个
拾取半径以内(等于其中一个永远选不中)。三个元凶,三种修法:

- **`head` 和 `face`。**占了绝大多数。face 这根骨头是从颅骨里指出来的,所以头一旦
  朝向或背对镜头,两个手柄就投影到同一个像素上(最近 1.8px)。修法:face 手柄改成
  一个**方向盘**——始终离头至少 2.4 个手柄半径,方向取投影后的朝向。关键是**不能
  因此丢掉深度**:把距离在 `[gap, reach]` 和 `[0, reach]` 之间做一次线性重映射,
  拖到盘的内圈仍然等于"正看着你"。
- **`hip` 根手柄。**它夹在 hipL / hipR 中间,把骨盆变成三个点的一堆。而它拖起来是
  **平移整个人偶**——拖身体本来就能做,而且更好发现。所以它是一个不产生新能力的
  手柄,砍掉(原则 9)。
- **缩短时肘和腕叠在一起。**这个躲不掉,是透视本身。改的是**拾取规则**:两个手柄
  距离差在三分之一拾取半径以内就算"并列",并列时**取链条更靠下的那个**——腕压肘、
  face 压 head。更细的那个控件永远是你想要的那个。

改完:**22%**,不可选的从 41 降到 8。有测试守着这两个数。

### 4.8 交互

选中人形工具时,画布是空的就**直接落一个站姿人偶**,不先问姿势(原则 2)。姿势库
只在选中某个人偶之后才出现在工具栏里,作用是**就地换姿势**——保持位置和身材,只换
关节(原则 10)。

| 动作 | 手势 |
|------|------|
| 摆姿势 | 拖关节:绕父关节旋转,**下面整条肢体跟着走**,三维骨长不变;拖得越短肢体越朝向镜头(§4.3);按住 Shift 送到身体背面,按住 Alt 只动这一个关节 |
| 移动 | 拖身体(命中任意骨骼或头部) |
| 转身 / 换机位 | 拖**左下角圆环**手柄:横拖转身,竖拖抬降机位 |
| 缩放 | 拖右下角方形手柄,绕人偶中心等比缩放,有下限防止缩成抓不住的点 |
| 换姿势 | 工具栏 Poses → 缩略图网格(按当前机位画) |
| 换机位 | 工具栏角度按钮(`35° / 8°`)→ 六个常用机位 |
| 摆头朝向 | 拖头前方那个**更小、空心**的手柄 |
| 镜像 / 删除 | 工具栏按钮;删除也可用 Delete/Backspace(输入框内不抢键) |

关节手柄**按景深改大小**:近的大、远的小。这不花钱,却让一个姿势的纵深在动手之前
就从手柄上读得出来。

命中优先级是关节 → 缩放手柄 → 身体 → 空白处取消选中。点一下只是选中,**不产生
undo 步**:快照在第一次 pointermove 时才入栈。

### 4.9 为什么不用现成方案

| 方案 | 结论 |
|------|------|
| [mannequin.js](https://github.com/boytchev/mannequin.js/)(three.js 关节人偶库) | 形态最接近,但 **GPL-3.0**。本仓库是 MPL-2.0 + 商业双授权,引入会污染商业授权那条线。否决。 |
| [open-pose-editor](https://github.com/ZhUyU1997/open-pose-editor)(3D OpenPose 编辑器) | MIT,three.js,但产出是 OpenPose 骨架 / depth / normal / canny——**全是 ControlNet 的输入**,我们的 provider 一个都收不到;而且它是一个完整应用,不是库。 |

第一版在这里写的是:真要上 3D,只能自己拿 three.js 加一个自有模型,**先不做**,等
2D 版被证明"方向对但表达力不够"再说。那一天到了——平面人偶说不出"手臂指向你",
也给不了机位,这不是调参能补的。

但结论仍然不是 three.js。走的是第三条路:**给现有的纯几何模型加一根 z 轴,外加
每个人偶自己的一台透视相机**。同一套 FK、同一个 canvas 2D 渲染器、同一份命中测试,
拿到的是透视缩短、遮挡排序和体积光影——也就是当初想从 3D 引擎那里要的东西。代价是
几百行纯函数,没有新依赖、没有 WebGL、没有资源加载,而且全部可单测。

| 方案 | 结论 |
|------|------|
| three.js + 自有人体模型 | 能给的比现在多(自遮挡的精确网格、IK、真实光照),但要引入 WebGL 运行时、一个要么打进包要么运行时拉的模型资源,以及一整套和 canvas 2D 草图层的合成问题。**收益递减,先不做**:现在缺的已经不是"不够立体"了 |
| 把姿势导成 OpenPose / depth 图 | 我们的出图链路一条都收不到(§4.1)。人偶的产物只能是像素 |

## 5. 实现要点

| 事项 | 做法 |
|------|------|
| 绘制 | Pointer Events(鼠标/触屏/笔一套代码),`setPointerCapture` 保证拖出画布不断笔;`getCoalescedEvents` 取浏览器合并掉的中间采样点,快速笔画是曲线不是折线;`touch-action: none` 防止手机把手势当滚动 |
| 坐标 | CSS 盒子按 `fitWithin` 等比缩到对话框内,永不放大超过 backing store;`toCanvasPoint` 把视口坐标映射回 backing store |
| 笔宽 | 相对 1024 画布定义,按 `max(w,h)/1024` 缩放,同一档在 512 和 1792 上视觉粗细一致 |
| 命中范围 | 关节/手柄的命中半径按**屏幕像素**给,再换算回画布单位,所以在 512 和 1792 上手感一致 |
| 撤销 | `StrokeHistory` 上限 30,每帧是笔画列表 / 人偶数组的快照(§3.2);`Ctrl/Cmd+Z` 绑定在对话框打开期间 |
| 导出 | 合成到另起的 canvas → `toBlob('image/png')` → `File`(`sketch-<ts>.png`),预览用 `toDataURL`,与上传图共用同一种 data URL 表示 |
| 挂载时机 | MUI Dialog 通过 Portal 延后一拍挂载子树,`[open]` effect 跑的时候普通 `ref` 还是 `null`。canvas 和舞台容器改用 callback ref → state,effect 在节点真正存在后再跑一次。这个坑第一版踩过:画布区域是空的、按钮永远 disabled |
| 打开参数 | 对话框只收一个 `initial: SketchLayers \| null`(就是参考图上已经存着的那个对象),必须是稳定引用:画布在它变化时重置,每次 render 新建一个就会抹掉用户正在画的东西 |
| 命中测试 | 打在 `figureParts` 真正画出来的形状上,不另立一张四肢宽度表——同一个物理事实两张表会走散,于是"能抓到的"和"看得见的"对不上。躯干和头是多边形,命中就是点在多边形内,用的是同一个点数组 |
| 尺寸基准 | 一切粗细、轮廓、最小尺寸、落点间距都以 `figureUnit`(髋→颈这根骨头,**量三维**)为单位,不用包围盒也不用投影长度:包围盒随姿势变,躺着的人会缩成火柴人;投影长度随机位变,转过去的躯干会把全身的粗细一起带没 |
| 投影 | 每个人偶一台相机,瞄准躯干中点,距离 3.4 个 `figureUnit`;近平面钳到 0.55 倍距离,所以一个被拖到贴着镜头的关节也不会把人偶投到无穷远 |
| 存档兼容 | 关节的 `z` 和人偶的 `turn` 都是可选的:三维化之前存下的草图重新打开时是一个正面朝前的平面人偶,然后就能被转起来 |
