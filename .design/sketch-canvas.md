# Sketch Canvas(生图 Playground 的草图与人偶输入)

> 适用对象:tingly-box 前端贡献者。
> 描述 Image Playground 的草图能力:在画布上画一张简图、摆一个人偶,作为参考
> 图像走 edit 链路生成。
> 关联文档:`ux-principles.md`(判断标准)、`imageedit.md`(edit 网关链路)、
> `image-slice.md`(同一 Playground 的后置切分)。

---

## 1. 背景

Playground 已经支持上传/拖拽/粘贴参考图,但有一类很常见的起点没有覆盖:用户脑
子里有个构图,手边没有图。之前的做法是去别的工具画一张、存文件、再回来上
传——三次跳转只为了一张"大概这样"的草图。

这个功能把画布直接放进 Playground:画完即成为参考图,prompt 说它该变成什么。
后来又补了人偶(§4),因为姿势和景别是文字 prompt 最控制不住的东西,而我们的出图
链路收不到任何姿势条件输入,能给模型的只有"参考图里的像素"——那恰好就是草图。

---

## 2. 核心决策

### 2.1 草图是参考图的一种来源,不是第三种模式

最初的备选是加一个 `Sketch` 模式。**否决**,理由:

- 草图与上传图在下游完全同构:同一个 `ReferenceImage` 列表、同一个请求、同一
  张历史卡片。给它单独开一个模式,是把"图从哪来"和"要做什么"两条正交轴拧到
  一个旋钮上(原则 4)。
- 混用是真实需求:一张产品照片 + 一张手画的构图示意,一起发给模型。分模式
  会把这种组合直接堵死。

这个判断后来推进了一步:Playground 原有的 Generate / Edit 模式切换也被拆掉了
(见 `imageedit.md` §6),参考图区永远存在、可选,端点按参考图数量推导。草图
入口因此不再需要先切模式。参考图的三种来源 **Browse / Paste / Sketch** 作为平
级动作并排呈现:空状态是虚线框里的三个文字按钮,已有图时是缩略图后面的三个
同样大小的方块(拖拽没有按钮,虚线框本身就是投放目标)。第一版把 Sketch 做成
了嵌在提示文字里的一个独立按钮,看起来像个外来物——来源之间没有主次,就不该
有一个长得不一样。`ReferenceImage` 多一个 `source: 'upload' | 'sketch'`
字段,除此之外提交链路零改动。

这条后来又挡住了一次扩张:人偶该不该做成第四种来源。不该,理由同上(§4.1)。

### 2.2 画布尺寸跟随 `Size`,而不是再选一次

画布的 backing store 直接取 Playground 当前的输出尺寸(`1024x1792` →
1024×1792 的画布),标题栏把具体像素写出来(`1024 × 1792 px · matches Size`,
原则 5)。用户不需要在对话框里再回答一次"多大、什么比例":模型收到的参考图
和它被要求输出的形状天然一致,不会出现草图是方的、结果被裁成竖的这种意外。

尺寸在打开时读一次,中途改 `Size` 要关掉重开。这条**现在是可以取消的将就**:
笔迹和人偶都已经是数据而不是像素(§3),按新尺寸重绘不再需要重采样。留着只是
因为还没做。

### 2.3 白底不透明,橡皮擦即"刷白"

画布永远是不透明白底,不做透明/有底的开关(原则 6)。透明草图对大多数图像模
型是含糊的输入——线条之外什么都没有,模型不知道该把它当白纸还是当蒙版。既然
底是白的,橡皮擦就是画白色,比画笔宽一档(擦是粗动作)。这样只有一条绘制路
径,没有 `destination-out` 合成模式的分支——这条便宜后来又收了一次利息:笔迹
改成矢量重放时,橡皮不需要任何特例(§3.2)。

### 2.4 固定小调色板,不做取色器

六个色:黑做轮廓,加五个模型能叫得出名字的纯色("把红色的圈改成太阳")。
取色器是一个用户没来这里做的决定;草图的信息量在形状,不在色号。

### 2.5 可再进入,而且是真的可再编辑

草图缩略图右下角有画笔按钮,点开是同一个画布,**原来的笔迹和人偶原样回来**,
提交时原位替换(保持它在参考图列表中的位置)。"用了"不等于"锁死"(原则 10)。
这也是 `source` 字段存在的唯一理由:上传图没有这个入口。

第一版的"可再进入"只做到一半:提交时一切被压平成 PNG,重开拿到的是像素,姿势
不再可调、撤销也断在保存那一刻。修法见 §3.3——那是本文档里唯一一次**推翻自己
先前的判断**,值得单独记。

### 2.6 prompt 的教育随场景切换

参考图里一旦有草图,prompt 的 placeholder 从"描述你想做的修改"换成"描述这张
草图应该变成什么"——草图和改图是两种心智,提示语跟着变(原则 8),但不替用户
写 prompt(与 `image-slice.md` §2 同一条原则:prompt 是用户的东西)。

画布上有人偶时,底部提示语同样换成"灰色人偶只是姿势参考,他是谁、穿什么由提示
词来说"。**不往 prompt 里塞"以骨架为姿势参考"这类句子**,哪怕那样成功率更高。

## 3. 画面是三层数据,不是一张位图

这是整个模块最核心的结构,人偶、撤销、再编辑三件事都从它长出来。

```text
backdrop   旧版压平的草图才有,一张底图                    ← 通常为空
strokes[]  每一笔:点串 + 颜色 + 粗细 + 笔/橡皮            ← 底层 canvas
figures[]  每个人偶:15 个关节 + 明度档位                  ← overlay canvas
```

底层 canvas 画笔迹,overlay canvas 画人偶,只要对话框开着,两层都还是数据。
overlay 只在人形工具激活时接收指针事件(`pointerEvents`),所以在人偶上继续画画
不需要先切模式。蓝色关节手柄只画在 overlay。

### 3.1 提交 = 合成,但原料一起交出去

```text
SketchResult {
  file, previewUrl,                 ← 发给模型的合成 PNG(含人偶,不含手柄)
  layers: { strokes, figures, backdrop }
}
```

合成走另起的一张 canvas,所以**手柄永远不会进入发给模型的 PNG**,而活的画布
保持分层。`ReferenceImage.layers` 收下 `layers`,**只服务编辑器**;请求链路仍然
只用 `file`,一行没改。

### 3.2 笔迹是点串,不是像素

一笔存的是它被画出来的那串点。画的时候仍然逐段直接画到 canvas 上(每次
pointermove 全量重绘看得见卡顿),**抬笔时这一笔才进列表**——一次手势 = 一个
undo 步,而且屏幕上已有的像素与重放的结果一致。

undo 只有一条栈,**每帧是整个画面状态**(笔画 + 人偶 + 底图),所以 Ctrl+Z 永远
等于"我刚才做的那一步",不管是哪个工具做的。之所以敢存整份而不是"只存被碰到的
那一层",正是因为两层都已经是列表:一帧只是两个数组引用 + 一个图片引用,而不是
1024² 的 `ImageData`(4 MB)。部分快照省不下什么,却要在撤销时把整份状态拼回来,
底图和图层因此走散过一次。

清空会把 backdrop 一起带走,否则"清空"之后画布会退回它打开时的那张图。

### 3.3 重开时把编辑态整个接回来

- 笔迹按列表重放,人偶回到对象层,**只有一个人偶时直接选中它**——手柄本身就是
  "这还能改"的回答,不该等用户先点一下才出现。
- **undo 历史用笔画列表反推**:第 i 帧就是前 i 笔。所以 Ctrl+Z 能一路撕掉保存
  之前画的笔画。人偶没法这样反推,它从保存时的姿势开始。
- 没有 `layers` 的草图(旧版本压平的)照常打开,当作可以继续画的底图,只是不再
  可摆、不再可逐笔撤销。

第一版把这些都压平了,理由是"不让 `ReferenceImage` 去迁就一个短生命周期的编辑
态"。**这个判断是错的**:摆姿势和画草图本来就是反复调的动作,一提交就锁死,等于
把原则 10 让给了数据结构的洁癖。代价也远比想象小——存的是数组,比第二张全尺寸
PNG 还省。

## 4. 人偶

### 4.1 它是画布里的一个工具,不是第四种参考图来源

我们的出图链路(OpenAI 兼容 generations/edits + Codex 原生 images)**没有任何一条
支持 pose 条件输入**,ControlNet 这类东西根本递不进去。所以一个人偶在我们这里
只可能是"参考图里的像素"——而那就是草图。结论和 §2.1 同一条:不开新入口,人偶是
Sketch 对话框里紧挨着 Pen / Eraser 的第三个工具。它改变的是"怎么起笔",不是
"图从哪来"。

同理,**场景布局不做成独立编辑器**——它要的是矩形/箭头/文字,属于 §6 里的画布
工具,做完那三样这个需求自然消失;而独立编辑器还多一个问题:块上的标签文字容易
被模型直接画进成品图。

### 4.2 画成木头关节人偶,不是火柴人

线条火柴人有一个具体的失败模式:模型把它**照着画进结果里**。实心人偶读起来是
"一个摆着这个姿势的身体",不是需要复现的线稿。

形体照美术用的木头关节人偶来:蛋形头 + 颈栓,胸廓和骨盆是**两个分开的体块**、
中间一颗腰球,肩肘腕髋膝踝是看得见的关节球,四肢是两头粗细不同的锥段,手是连着
小臂的连指块,脚是横在小腿末端的块。这不是装饰——**胸廓的横轴挂在肩线上,骨盆
挂在髋线上**,所以拖一侧肩膀只有胸廓跟着转,骨盆不动,躯干因此有了扭转和正背面。
一排等宽胶囊给不了这个信息,而姿势参考图里最值钱的恰恰是它。

几何全部从那 15 个关节推导(`figureParts`),**没有额外的手柄**:结构变好看不以
增加用户要操作的东西为代价。

三条踩出来的渲染经验:

- **画序和形状一样重要。** 髋球画在骨盆块**下面**,只在大腿接缝处露出一牙;压在
  上面会立刻变成两瓣屁股。骨盆本身要宽过髋球、矮过一个球径,否则会从髋线上吊下来
  成一颗水滴。其余关节球画在体块之上,它们本来就长在轮廓外。
- **体块各自旋转会散架。** 把肩膀往下拽很远时,胸廓会从脖子底下转出去、露出缝。
  所以躯干底下永远先画一根 neck→髋中点的锥形"脊柱",人偶在任何关节角度下都是连
  着的。
- **轮廓要有一圈 rim。** 每个部件画两遍:先按 rim 宽度整体外扩画一遍纯色,再原
  尺寸画本体。第一遍是同一个颜色,部件之间的接缝自己消失,剩下的正好是整个人偶的
  外轮廓,不需要求并集。没有它,人偶贴着白纸会化掉,两个交叠的会连成一块。

配色三档(躯干 / 关节球更深 / 头更浅),中性灰,不做渐变、不用木色:结构才是信息,
木色只会邀请模型画一个木头娃娃。只提供这一种画法,没有开关(原则 6);如果某个
provider 仍然照抄人偶,该调的是这里的渲染,不是把选择推给用户。

### 4.3 骨架:关节有父子,骨长不变

根在髋中点,髋→左右髋→膝→踝,髋→颈→左右肩→肘→腕,颈→头。拖一个关节是让它
**绕父关节转**、并带着整条子链刚性跟随,所以骨长永远不变——散点拖拽能把小臂拉成
橡皮筋,而木头人偶做不到这件事。拖根关节就是移动整个人偶。少数需要怪比例的情况
按住 Alt,退回单点拖拽。

### 4.4 姿势库

四个预设按钮撑不到二十多个姿势,所以工具栏上只留一个 **Poses**,点开是分组的
缩略图网格(站姿 / 动作 / 坐卧 / 手势),点一个就地换姿势。

- **姿势用角度声明,不写坐标。** 一个姿势是"上臂 -50°、小臂 25°"这种可以在脑子里
  想象的东西;三十个坐标数字不是。角度是**骨头自身的绝对角**(0 朝下、+90 朝右、
  ±180 朝上),不是相对父骨——相对角写起来更"对",但读的时候要在脑子里做累加。
  `lean` 是唯一的例外(它扳的是躯干顶端),负值让身体朝四肢伸出去的那一侧倾。
- **所有姿势共用一套骨长。** 这是硬要求,不是整洁癖:拖拽已经是绕父关节旋转、骨长
  不变(§4.3),库里的姿势若各自骨长不同,换一个姿势就会悄悄改变这个人的身材。单测
  直接断言了这条。归一化也因此用**同一个缩放**,而不是"把每个姿势拉满整个盒子"——
  蹲着的人本来就比站着的矮,拉满会把蹲变成站。换姿势时对齐的是**躯干骨长**而不是
  包围盒高度,同理。
- **缩略图就是同一个渲染器画的**,不是另画一套图标。姿势库唯一的价值是"点到的就是
  拿到的",图标集会在人偶下次改动时立刻失真。缩略图按格子等比缩放,否则展臂和躺
  这些最需要认出来的姿势恰好会被裁掉。

角度是可以在脑子里想象,但想象会错:第一版的跑步手臂折在胸前、蹲是往后坐、鞠躬和
伸手的躯干朝向反了。**改姿势就把 21 个全渲染成一张对照表看**,比单看一个快得多。

### 4.5 多个人偶

一个画面里放两三个人是常见需求(对话、合影、人群),所以多人偶要能用,不是能存在:

- **落点**:新人偶从画布中心向外找第一个空位,不叠在已有的人身上。全占满了就级联
  偏移,至少保证抓得到。
- **明度**:同一个灰的两个人偶一旦交叠就糊成一坨,模型连画面里有几个人都读不出来。
  所以人偶有三档明度,**创建时定死、存进数据**——按列表位置上色的话,删掉一个会让
  其余的集体变色。只调明度不换色相,它们仍然是同一种材质。
- **叠放时的选中**:点一摞人偶是**往下走**,不是永远选最上面那个,否则底下的永远
  够不着。选中态的冷色调覆盖在明度之上,所以"选中的是哪个"任何时候都清楚。

### 4.6 交互

选中人形工具时,画布是空的就**直接落一个站姿人偶**,不先问姿势(原则 2)。姿势库
只在选中某个人偶之后才出现在工具栏里,作用是**就地换姿势**——保持位置和身材,只换
关节(原则 10)。

| 动作 | 手势 |
|------|------|
| 摆姿势 | 拖关节:绕父关节旋转,**下面整条肢体跟着走**,骨长不变;按住 Alt 只动这一个关节 |
| 移动 | 拖身体(命中任意骨骼或头部) |
| 缩放 | 拖右下角方形手柄,绕人偶中心等比缩放,有下限防止缩成抓不住的点 |
| 换姿势 | 工具栏 Poses → 缩略图网格 |
| 镜像 / 删除 | 工具栏按钮;删除也可用 Delete/Backspace(输入框内不抢键) |

命中优先级是关节 → 缩放手柄 → 身体 → 空白处取消选中。点一下只是选中,**不产生
undo 步**:快照在第一次 pointermove 时才入栈。

### 4.7 为什么不用现成方案

| 方案 | 结论 |
|------|------|
| [mannequin.js](https://github.com/boytchev/mannequin.js/)(three.js 关节人偶库) | 形态最接近,但 **GPL-3.0**。本仓库是 MPL-2.0 + 商业双授权,引入会污染商业授权那条线。否决。 |
| [open-pose-editor](https://github.com/ZhUyU1997/open-pose-editor)(3D OpenPose 编辑器) | MIT,three.js,但产出是 OpenPose 骨架 / depth / normal / canny——**全是 ControlNet 的输入**,我们的 provider 一个都收不到;而且它是一个完整应用,不是库。 |

真要上 3D(能拿到透视缩短和机位,2D 拖关节永远给不了),只能自己拿 three.js 加
一个自有模型。**先不做**:模型到底吃不吃姿势参考还没验证,3D 是一种昂贵得多的失败
方式。等 2D 版被证明"方向对但表达力不够"再说。

## 5. 实现要点

| 事项 | 做法 |
|------|------|
| 绘制 | Pointer Events(鼠标/触屏/笔一套代码),`setPointerCapture` 保证拖出画布不断笔;`getCoalescedEvents` 取浏览器合并掉的中间采样点,快速笔画是曲线不是折线;`touch-action: none` 防止手机把手势当滚动 |
| 坐标 | CSS 盒子按 `fitWithin` 等比缩到对话框内,永不放大超过 backing store;`toCanvasPoint` 把视口坐标映射回 backing store |
| 笔宽 | 相对 1024 画布定义,按 `max(w,h)/1024` 缩放,同一档在 512 和 1792 上视觉粗细一致 |
| 命中范围 | 关节/手柄的命中半径按**屏幕像素**给,再换算回画布单位,所以在 512 和 1792 上手感一致 |
| 撤销 | `StrokeHistory` 上限 30,每帧是笔画列表 / 人偶数组的快照(§3.2);`Ctrl/Cmd+Z` 绑定在对话框打开期间 |
| 导出 | 合成到另起的 canvas → `toBlob('image/png')` → `File`(`sketch-<ts>.png`),预览用 `toDataURL`,与上传图共用同一种 data URL 表示 |
| 挂载时机 | MUI Dialog 通过 Portal 延后一拍挂载子树,`[open]` effect 跑的时候普通 `ref` 还是 `null`。canvas 和舞台容器改用 callback ref → state,effect 在节点真正存在后再跑一次。这个坑第一版踩过:画布区域是空的、按钮永远 disabled |
| 打开参数 | 对话框只收一个 `initial: SketchLayers \| null`(就是参考图上已经存着的那个对象),必须是稳定引用:画布在它变化时重置,每次 render 新建一个就会抹掉用户正在画的东西 |
| 命中测试 | 打在 `figureParts` 真正画出来的形状上,不另立一张四肢宽度表——同一个物理事实两张表会走散,于是"能抓到的"和"看得见的"对不上 |
| 尺寸基准 | 一切粗细、轮廓、最小尺寸、落点间距都以 `figureUnit`(髋→颈这根骨头)为单位,不用包围盒:包围盒随姿势变,躺着的人会缩成火柴人 |

## 6. 未做 / 后续

  运行时拉,是个要单独决定的事,不该顺手加。
