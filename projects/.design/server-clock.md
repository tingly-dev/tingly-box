# 计时以服务器时钟为准

## 问题

续一个聊天时，transcript 底部的"Thinking"一开始就显示 3m，之后从 3m 往上走。

原因不在计时逻辑：事件的 `created_at` 是服务器时钟打的，而"已运行多久"、"3m ago" 是拿它和浏览器的 `Date.now()` 相减。服务器时钟和浏览器时钟差几分钟（服务器没对时、WSL / 虚拟机时钟漂移、服务器在远端）时，所有计时都从这个差值开始。实际遇到的是服务器时钟慢了约 3 分钟（`timedatectl` 显示 `System clock synchronized: no`）。

## 决定

- 每个 API 响应都带服务器的 `Date` 头。`client/index.ts` 里所有请求（`api` 和 `apiFetch`）都经过 `observedFetch`，把它记给 `utils/serverClock.ts`。
- `serverNow()` = 浏览器时钟 + 最近一次测得的偏移。`WorkingLine`、后台任务的计时（`useNow`）和 `timeAgo` 都用它代替 `Date.now()`。
- `Date` 头只有整秒且向下取整，所以取半秒作中点；精度本来就只是参考值（约 ±1 秒）。以最新样本为准，但新样本与当前偏移相差不超过 1.5 秒时不更新（死区），免得计时在 1s、2s、1s 之间跳；差得更多说明某一端的时钟被校准或步进过（休眠唤醒、NTP），就跟着走，两个方向都一样。
- 带 `Age` 头的响应是缓存的，它的 `Date` 是当初生成的时间，直接跳过。
- 桌面窗口跨域访问网关，浏览器默认不让脚本读 `Date`：`middleware.CORS` 加了 `Access-Control-Expose-Headers: Date`。

## 被否决的做法

- **保留见过的最大偏移**（延迟、取整只会让服务器看起来更落后）。浏览器时钟被步进、或服务器被校准后偏移只增不减，永久错一个步进量，要刷新页面才恢复。
- **服务端另外下发 `now` 或已运行时长。** 要改每个接口；`Date` 头是现成的、每个响应都有。
- **从收到事件的那一刻起计时。** 刷新页面或打开一个正在跑的线程时没有这个时刻，还是得用服务器时间戳。
- **只修提示"时钟不同步"。** 用户看到的是错的计时，而不是一条警告。

## 限制

偏移只在有响应时更新；页面放着不动、时钟又漂移时会慢慢走偏，下一次请求（事件流重连、操作）就会纠正；事件流只在连接时量一次。`Date` 头被代理或嵌入宿主的 `fetch` 去掉时退回浏览器时钟，行为和以前一样。
