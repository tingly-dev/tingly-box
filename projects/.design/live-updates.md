# 实时更新：列表靠事件流，不靠重拉

> Issue：[#2182](https://github.com/tingly-dev/tingly-box/issues/2182)。PR：#2183（列表）、堆叠在其上的 transcript PR。状态：已实现。
> 总体实时模型见 `projects.md` §4.6；这里记录"页面上的数据怎样保持新鲜"这一决定，以及被否决的做法。

## 问题

Projects 的项目列表（侧栏、文件夹页、IM 项目目录共用一份，`projectListStore`）原来的刷新规则是：

- 全部项目事件流（`/projects/events`）上每来一个 `thread` / `project` 事件，就重拉一次 `GET /projects`（300ms 防抖）；
- 另外每 30 秒轮询一次；
- 事件流重连、标签页回到前台、页面报告变化时也重拉。

`thread` 事件里本来就有变化后的线程，但列表需要的是"每个项目各状态的线程数"，事件里没有，前端无法就地更新，只能整表重拉。于是**任何项目里任何线程状态一变，每个打开的页面都整表重拉一次**，服务端每次还要对整个线程表做一次 `GROUP BY`。

另外两处放大了这个问题：

- 服务器 `WriteTimeout: 10m` 也作用于 SSE 长连接，每 10 分钟断一次。每次重连，文件夹页会重拉列表、所有列出文件夹的线程、当前会话的完整 transcript；项目页重拉项目、200 条消息和打开的线程。
- 文件夹页上后台任务（`background_tasks_changed` 等）每变一次，就连同完整 transcript 一起重拉线程。

实测（`main` f4a53b8，1 个项目 + 6 个文件夹，6 个线程每 4 秒收一条消息，统计 60 秒）：文件夹页、无关项目页的 `GET /projects` 都是 **20 次**；空闲时 7 次。

## 决定

**事件带上列表需要的结果，前端只改受影响的那一行；整表请求只在"不知道"的时候发。**

1. **`thread` 事件携带项目计数。** `Event` 增加可选字段 `threads`（`db.ThreadCounts`），值是该项目在这次变化之后的各状态线程数。所有发布 `thread` 事件的地方都走 `Threads.publish`，它对单个项目做一次按 `project_id` 的 `GROUP BY`（有索引）。
2. **列表就地更新。** `projectListStore` 收到 `thread` 事件时用 `threads` 替换那一行的计数；收到 `project` 事件时把字段合并进那一行，`archived_at` 非空则移除该行；记忆变化（`{memory}`）不影响列表，忽略。
3. **只在不知道时重拉。** 以下情况才发 `GET /projects`：事件里的项目不在列表中（别处新建、取消归档）、事件缺少 `threads`（旧服务端）、流重连、标签页回到前台、页面报告变化（`PROJECTS_CHANGED`），以及 5 分钟一次的兜底轮询。
4. **事件流不受 `WriteTimeout` 限制。** `stream()` 开始时用 `http.ResponseController` 清除写超时；断线只来自真实的网络问题，不再是定时的。
5. **后台任务变化只读线程。** 实时任务集合在 `GET /threads/:id` 里，transcript 已经由事件流送达，所以不再一起重拉 `/threads/:id/events`。

结果：同样场景下 `GET /projects` 从 20 次降到 4 次/分钟（剩下的是首次加载和左侧导航栏红点自己的 30 秒轮询，见"后续"）。

## Transcript：首屏一页，之后只读变化

列表修好之后，最重的是 transcript：打开、切换会话、刷新、重连、发完一条消息（项目对话会重拉 200 条），都从头整段读 `GET /threads/:id/events`，没有上限。长会话里 tool_result 很大，一次就是几百 KB 到几 MB。

1. **`thread_events.updated_at`**（UTC，有索引）。新增时写入，`UpdateThreadEvent`（审批、提问被回答，流式回复收尾）时更新。迁移把旧行回填为 `created_at`。
2. **`GET /threads/:id/events` 三种读法**：`?limit=N` 取最新 N 条；`?limit=N&before=<event id>` 取它之前的 N 条（往上翻页）；`?since=<RFC 3339>` 取 `updated_at >= since` 的全部条目（新增的和原地改过的）。前两种返回 `more` 表示更早的还有没有。
3. **前端 `useTranscript(threadId)`**（项目对话、项目页的线程面板、文件夹页共用）：
   - 第一次打开读最新 100 条，顶部有"显示更早的消息"，加载后保持阅读位置不跳。
   - 读过的线程留在页面级缓存里（最多 20 个）。切回去先显示缓存，再用 `since` 补齐变化；重连、发送消息后也只做 `since`。
   - `since` 取已加载条目里最大的 `updated_at`，截到毫秒（向下取整）。因为是 `>=`，只会多拿、不会漏，重复的按 id 覆盖。
   - 一个比已加载窗口更早的条目被改了（很早的审批被回答），只在已加载时替换，不插入，避免窗口顶部出现断层。
   - 同一线程的补读在飞时，后来的补读共用这次请求；切换线程后旧请求的结果即使在线程切回时才返回也会丢弃。
   - 首次读取返回之前从事件流到达的条目会先按线程暂存，读到后只清理并合并该线程的条目。

此前页大小为 200 时实测（464 条的会话）：打开读 200 条约 56KB；切到别的会话再切回只读 `since`，390B；刷新页面仍只读一页，不再是全部。

### 子代理的步骤单独分页

每个线程（文件夹会话和项目线程）都把子代理（Agent 调用）的每一步存成 `parent` 为该调用 `request_id` 的条目，任务事件也一样存（卡片靠它判断子代理的状态）。项目线程原来丢掉这些步骤，只为让线程视图只显示主对话；分页把步骤和主对话分开读之后，这个理由不存在了，丢掉反而让项目线程里的子代理没法查看。一个子代理可以有上千步，如果和对话混在一起分页，最新一页可能全是它的步骤，主对话一条也看不到；而且只拿到一半的步骤会挂在一个没加载的 Agent 调用下面，成了孤儿。

1. **对话分页只算主线。** `limit` / `before` 只读 `parent = ''` 的条目；`?parent=<Agent 调用 id>` 用同样的 `limit` / `before` 读那个子代理的步骤。`since` 不分主线和子代理，返回全部变化。
2. **步骤在展开时才读。** Agent 卡片第一次展开时读该子代理最新 100 步，顶部有"显示更早的步骤"。首次主线分页不带未展开的步骤；`since` 补读目前仍可能带回它们，见“后续”。
3. **用量随页带全。** 状态栏的 token 合计要所有 `usage` 条目，所以主线页还有更早内容时（`more`），服务端把这页之前的全部 `usage` 条目一起返回。它们很小，前端定窗口起点时跳过它们。
4. **只画能挂上的步骤。** 父调用没加载的子步骤不画（翻到那一页时再出现）；挂在已加载的非 Agent 调用下的照样画。

此前页大小为 200 时实测（一个子代理 1200 步的会话）：打开读 200 条主线约 56KB，不含任何子代理步骤；展开卡片读 `?parent=agent1&limit=200`，"显示更早的步骤"再读 `before` 的一页。

### 找到并单独查看一个子代理

分页之后，一个子代理可能在没加载的那段历史里，卡片也只适合看几十步。所以子代理要能脱离对话被找到、被单独打开，再回到它在对话里的位置。

1. **列表不读 transcript。** `GET /threads/:id/subagents` 列出会话的每个 Agent 调用：描述、类型、状态、步数、调用事件的 id。全部来自调用、结果和任务事件上的一次聚合，不含任何步骤或报告正文。入口在会话菜单的"子代理"。
2. **单独打开。** 列表的一行或卡片上的"单独查看"把对话区换成这个子代理：要求、步骤、报告，顶部"显示更早的步骤"保持阅读位置。调用本身不在已加载的页里时，用 `?call=<request id>` 只读它自己的几条事件（调用、结果、任务事件）。步骤仍然走 `?parent=`。
3. **在对话中查看。** `?from=<事件 id>&before=<窗口第一条>` 一次读回从这个调用到已加载窗口之间的主线，然后滚到卡片并闪一下。后台任务面板和轨迹视图的"在对话中查看"也走这条路，不再对没加载的调用静默失败。

为什么是 `from` 而不是 `around`：只读目标附近一段会在它和已加载窗口之间留下空洞，就得再做"向后翻页"和断层提示。`from` 只读主线（不含子代理步骤），窗口始终连续，"显示更早的消息"照旧工作。代价是目标很早时一次读得多一些，但仍远小于整段 transcript。

为什么不用按 id 的 `after` 游标：审批、提问、流式回复都会原地修改已有条目，按创建顺序的游标会漏掉这些修改，所以游标必须基于"最后写入时间"。

## 不变量

- **计数是快照，不是增量。** `threads` 是变化后的绝对值，所以丢一个事件（Hub 对跟不上的订阅者会丢事件）只会让那一行暂时过期，下一个同项目事件就自愈；不需要序号或重放。
- **正在进行的整表请求不能覆盖更新的事件。** 请求发出后到达的行更新记在 `sinceFetch` 里（同一行的多次更新按顺序合成），请求返回后再叠加到结果上。没有选择"丢弃这次请求并重发"，因为持续活跃时它会变成循环重拉，正是要消除的东西。
- **隐藏的标签页照样应用事件，但不发请求。** 回到前台时补拉一次。

## 被否决的做法

- **前端自己推算计数**（记住每个线程的旧状态，收到事件时一减一加）。列表里没有全部线程，事件也不带旧状态；第一次见到的线程无法得知它原来算在哪一组，只能靠重拉兜底，复杂度高且仍会漂移。
- **事件里推整张项目列表。** 每个事件的体积随项目数增长，所有订阅者都收全量，等于把重拉从 HTTP 挪到 SSE。
- **`GET /projects` 加 ETag / 304。** 能省下传输，但请求次数和服务端的 `GROUP BY` 都不变。
- **完全去掉轮询。** 事件可能被丢，或者中间代理缓冲 SSE 导致流"连着但不出数据"；5 分钟一次的兜底代价很小。
- **给 transcript 加 `after=<event id>` 游标**。见上：原地修改会被漏掉，改用 `updated_at` + `since`。
- **把 transcript 缓存到 localStorage / IndexedDB 跨刷新复用**。刷新后首屏只是一页（几十 KB），换来的是缓存失效、容量和多标签页一致性的问题，不值得。

## 代价

- 每个 `thread` 事件多一次单项目计数查询。和原来"每个打开页面各做一次全表 `GROUP BY` + 整表传输"相比可以忽略。
- `Event` 多一个可选字段，旧前端忽略它，行为不变；新前端遇到不带该字段的旧服务端回退到重拉。

## 后续（#2182）

- `?since=` 目前也会带回未展开的子代理步骤。不能只加查询条件排除它们：游标取已加载条目的最大 `updated_at`，新展开的子代理步骤可能推进游标，盖掉之前未读到的变化；需要重新设计游标或补读规则。
- 左侧导航栏红点（`useProjectsWaiting`）仍独立每 30 秒拉 `GET /projects`；它在主 bundle 里，不能直接引用 Projects 包的 store。
- IM 绑定在每个项目 / 文件夹页上每 15 秒轮询，即使没有绑定任何聊天；应改为事件驱动。
- "全部文件夹"视图对每个有线程的文件夹各发一次 `GET /projects/:id/threads`；应有一个跨文件夹的接口。
